# 跨渠道搜索设计

在路线前预研和路线确认后的补查中使用。本文件管理研究问题与查询设计；工具参数仍按供应商 Skill，来源与审查按多来源研究契约。

## 从游客的问题开始

先从 brief 确认目的地和用户要了解的问题：有什么值得吃、值得玩，哪些适合用户。旅行天数、人数、预算和节奏用于读取结果后的取舍与排程，不直接拼进发现关键词。月份、自驾、停车等条件仅在已发现候选的具体问题确实需要时补查，不在首轮堆叠。

网页和小红书的首轮用“目的地 + 推荐类别”发现选择，例如“宜昌美食推荐”“宜昌旅游推荐”；“目的地旅游攻略”“目的地小吃推荐”可作为需要时的自然替代表达。先搜索并读正文、图片和评论，再知道当地值得吃什么、玩什么；不能先由模型确定菜品、门店或景点，再只搜证据。默认不把旅行天数或几天几夜加入小红书关键词；用户明确要求查某种天数攻略时才按该请求搜索，并记录原因。普通多日行程仍先发现候选，再由 Agent 按实际天数组合路线。

一条查询只回答一个主要问题。具体景点、菜名、店名由用户指定或已读结果带出，再单独补查；保留发现它们的查询与来源。泛化美食发现不要预先塞入多个已知菜名或门店，把搜索范围收窄到模型已有印象。少量语义相近的替代表达用于解决实际缺口，不为凑次数重复检索。

## 逐步缩小范围

| 阶段 | 要回答的问题 | 网页与小红书示例 |
| --- | --- | --- |
| discovery：发现选择 | 这里有什么值得玩、吃、住的选择 | “目的地旅游推荐”“目的地美食推荐”“目的地小吃推荐”“目的地住宿推荐” |
| discovery：补充需求 | 哪些选择符合这次旅行 | “目的地慢游攻略”“目的地早餐推荐”“目的地十月旅游攻略”“实际用餐县城美食推荐” |
| detail：了解对象 | 某个已发现对象如何玩、吃，值得什么代价 | “具体景点游玩攻略”“已发现菜品哪家好吃”“具体门店评价” |
| verification：核验条件 | 已选对象能否在本次日期执行 | “具体景区官方预约”“具体分店菜单”“具体酒店停车充电”“具体线路官方船班” |

先形成候选，再按用户兴趣、天数、预算、地理方向和体力筛选，不照搬某篇相同天数攻略。用户已指定的对象可以直接补查详情，但不能代替仍需的开放发现。具体对象查询须能追溯到用户指定或前面的发现来源；覆盖不足时回到开放查询。路线确认前只提取玩法、区域、地方吃法和取舍，不推荐具体门店、不查库存。不能用只有店名核查或官方规则核查的结果，声称完成了目的地选择发现。

## 按渠道表达同一个问题

- **网页**：先搜索自然语言问题并读攻略、地方介绍或亲历资料；出现候选后分开查具体对象与官方规则。开放发现不默认加“官方”、站点限制、年份和大量条件。需要核验时再加对应主体、日期或 `site:`；页面发布时间和适用日期以原文为准。
- **小红书**：首先用“目的地美食推荐”“目的地旅游推荐”分别发现吃与玩，省略旅行天数、预设对象、出发地及“亲历体验”等研究术语。读取正文、图片和评论形成候选后，再按缺口查具体玩法、口味、排队或避坑；不能跳过发现阶段直接搜已知景点组合。先无筛选获取候选，挑不同作者、相关正文和必要图片读取；高点赞、靠前排名和标题匹配都不能代替正文判断。不机械取第一个匹配或第一个返回结果。
- **高德**：查询对象与查询空间分开。已知门店逐家用名称查 POI，结合城市、分店和地址消歧；不同门店不拼成一条关键词。找附近餐饮先取得用餐锚点坐标，再用 `maps_around_search(location, keywords, radius)`，关键词为“餐厅”或一种相关菜系；“地标 周边 餐厅”的文字查询不能证明位于指定半径内。候选再读详情，并按实际前后路线比较。文字搜索、评分和返回顺序都不等于推荐。

同一主题可以由多个渠道补证，每次查询仍记录实际使用的工具和条件。不要把网页、小红书、高德的多次输入事后合成一串“综合关键词”。

## 根据内容和缺口决定下一次查询

执行前按[调用范围与执行效率](execution-efficiency.md)检查本次行程的同条件查询与已读来源；能回答当前问题且仍有效时复用，参数变化或实际缺口才补查。复用保留原查询与来源时间，不登记为新的平台调用、不增加独立样本；包装输出 execution.mode 会区分 fresh/reused。

读结果后记录回答了什么、仍缺什么、哪个候选值得继续查及理由。餐饮正文中的地方吃法要完整提取为待核候选，再按用户口味、餐窗、预算和绕行取舍；不能只摘出模型事先知道的两三种食物。图片承载信息时按小红书看图规则读取。

候选偏少、无结果或结果偏题时，先检查是否堆叠了多个菜名、对象或地点；拆成单一问题，或返回更宽的发现查询。再按缺口补餐别、片区、季节或用户限制。记录旧查询与新查询的关系、结果变化和未采用原因，不把一次窄查询无结果写成“当地没有餐厅/没有攻略”。遇到工具故障或风控仍遵循供应商的重试与停止规则。

停止条件是实际问题已有足够、相关且可执行的答案。查询次数、结果数量或读过几篇不能证明研究完成。语义审查要核对玩法与美食是否符合偏好、完整旅行日餐窗是否落实、候选是否重复，以及来源是否真正支持推荐。

## 单次查询记录

新工作区设置 `research_contract.query_design_version=1`。`queries[]` 每项对应一个实际执行的查询；规划中的词不能提前记为成功。查询执行后及时记录：

- `id`：稳定查询 ID；`scope` 沿用 play/eat/operations/route/general。
- `stage`：discovery/detail/verification；`purpose`：本次要解决的具体问题。
- `channel`：获取方式；`provider`：平台 ID，如 web/xiaohongshu/amap；`tool`：实际工具名。
- `query`：实际关键词；没有关键词的详情或路线调用记录公开对象 ID 或起终点说明。
- `parameters`：实际非敏感输入，包括搜索条件、城市、半径、公开 POI/笔记 ID 等。Cookie、Key、临时令牌和带签名媒体地址全部省略，不能复制原始响应。
- `checked_at`、`status`：执行时间与 success/no_results/failed；失败或无结果写 `reason`。
- `result_count`：可取得时记录本次返回的候选数量，不是平台总量或有效推荐数量。
- `outcome`：哪些内容有用、采用或舍弃的理由、剩余缺口与下一步。搜索成功但尚未读取候选时可没有 `source_ids`，此时不声称已有可用证据。
- `source_ids`：实际读取并归档的来源；详情读取后回填发现查询，不能借其他平台的来源填空。后续补查可用 `parent_query_id` 指向触发它的查询。

自动审查检查记录完整性、引用和平台归属；无法判断关键词的语义质量或证明真实执行。主 Agent 须核对首轮是否实际开放搜索吃与玩、是否无理由带入天数、具体对象是否来自用户或已读结果、是否提取正文/图片/评论的新候选，以及结果取舍是否依据用户需求而非模型先验名单。旧工作区保持可读；重新研究采用新记录，不改写历史关键词掩盖错误调用。

## 代码入口与自动记录

正式小红书旅行发现使用 `xhs-discover`，由代码生成关键词，不拼接 brief 的旅行天数：

```bash
python3 skills/travel-planning/scripts/research_sources.py xhs-discover \
  --destination "宜昌" --topic eat --workspace ".travel-research/<trip-id>"
python3 skills/travel-planning/scripts/research_sources.py xhs-discover \
  --destination "宜昌" --topic play --workspace ".travel-research/<trip-id>"
```

分别生成“宜昌美食推荐”“宜昌旅游推荐”。多城市分开传单个目的地。需要其他自然开放表达时，带工作区的 `xhs-search` 允许目的地加“美食推荐/小吃推荐/旅游推荐/旅游攻略”，空格不改变判定；首轮不允许堆叠对象、时长和限定条件。

具体对象来自已读发现资料后，先登记该来源，再补查：

```bash
python3 skills/travel-planning/scripts/research_sources.py xhs-search \
  --keyword "已发现门店评价" --destination "宜昌" --topic eat \
  --search-stage detail --target-source-id <发现来源ID> \
  --workspace ".travel-research/<trip-id>"
```

代码检查同目的地、同主题的前置成功开放发现和来源存在；具体名称是否真的出现在该原文中仍须 Agent 语义核对。用户明确指定对象或某种天数攻略时，用 `--search-stage detail --user-request "用户的明确要求"` 记录例外；不能由 Agent 为绕过门槛虚构用户要求。其他条件补充也属于有来源的后续查询。无 workspace 的通用搜索保持兼容，不能据此声称完成旅行研究。

包装调用自动保存 `evidence/<task-id>/xhs-searches/`，包含真实关键词、阶段、目的地、主题、返回候选数、交给 Agent 的截取数量、全部返回候选的笔记 ID、状态和查询时间。返回数量只计算实际返回的笔记卡，不是平台总量；失败数量为未知，不记虚假0。复用不增加记录或刷新时间，搜索上限只限制输出，不抹掉原始返回数量；不保存临时令牌。

吃、玩开放发现完成后，用批量采样器顺序读取候选详情和有限评论样本：

```bash
python3 skills/travel-planning/scripts/research_sources.py xhs-sample \
  --workspace ".travel-research/<trip-id>" --task-id main
```

采样器复用已成功归档的详情，按 `note_id` 去重；优先补足吃/玩各5篇，再补至每个目的地共15篇。只把与该目的地成功开放发现候选相交、且有有效详情/评论归档的独立笔记计入配额。新工作区评论 v2 每取得一篇返回 `status=awaiting_review`，先用 `xhs-review` 分批阅读所有已取得讨论串，在 itinerary-plan.json 保存逐帖结论后继续运行采样器；这不是服务失败，也不表示已完成研究。返回 `status=complete` 才表示配额达标且没有待审查笔记；若候选不足或采集中出现登录、风控、限流、连接或详情解析失败，会停止并返回已读量、各主题缺口及失败类别。先补充搜索候选或处理本人登录/平台问题，再重新运行；不得通过重复详情、手填计数或扩大评论显示总数补足。

装配器自动导入 `planning.xhs_search_records[]`；新工作区强制 `xhs_search_design_version=1`，不能在计划中关闭。最终审查和渲染拒绝缺记录、窄词冒充发现、无用户要求的时长词、无前置发现/来源的具体查询，以及数量与候选列表不一致。旧行程保持兼容；历史不足不补造。

新工作区清单启用 `xhs_detail_sampling_version=1`。装配后带此版本的最终行程须通过详情采样硬门槛：每个被研究目的地有至少15篇独立详情/评论观察，且 eat、play 各至少5篇；只统计搜索记录中对应成功开放发现的候选。门槛同时由 `audit_itinerary.py` 和渲染器调用的研究审计执行，缺口会阻断 final。旧工作区没有该版本时保持原有兼容行为，不为历史记录补造采样量。
