# 餐饮研究与路线适配

餐饮与游玩共同决定每天的片区。先研究地方吃法和用户饮食偏好，再结合景点、住宿与交通建立餐窗；精确路线在出入口稳定后完成。美食偏好行程同时回答“吃什么、在哪吃、何时吃、为什么适合”，不以附近填空替代推荐。

## 多来源发现

先按[研究深度](research-depth.md)区分普通区域餐窗与重要门店体验。普通餐保留时间、具体街段、正餐供给依据与备用补给，使用 mode=area，不默认逐餐搜主备门店和双腿路线。下方候选四阶段与门店证据只用于 detailed 餐窗；美食偏好仍优先落实核心特色餐和地方吃法多样性，不能把所有餐都降为普通区域建议。

先按[跨渠道搜索设计](search-design.md)用“目的地美食推荐”“目的地小吃推荐”等自然问题发现地方吃法，再按实际餐别与用餐片区补查。由已读内容提出菜品和门店候选，逐家核验；不把多个预设菜名、店名和街区拼成发现查询。高德附近餐饮用坐标与半径搜索，再核对分店与前后路线。

遵循[多来源研究契约](multi-source-research.md)。**网上搜索是主动研究路径，小红书与高德都可用时也搜网页。**公开攻略、媒体、文旅的地方风味介绍、商家菜单、亲历游记、社区和地图都可提供候选，再按问题交叉验证。文旅宣传只能发现地方菜，商家菜单可证明具体分店提供什么，独立亲历资料支持口味与体验，地图核对身份与路线。

小红书可用时补充正文、必要图片和评论；正文空不能直接丢图。高德可用时优先核对分店、地址、坐标、营业、人均与评分实际字段。二者未配置时继续网页研究，不自动安装或登录，不因缺辅助工具给整趟行程判失败。公开页面仅在合法可读时使用，不绕过风控。搜索摘要只作发现，采用结论需读原文。

按重要问题和缺口分配查询预算，同一证据在本次行程复用。小红书默认每城最多4次搜索、6条详情、6张相关图片；高德默认最多4次发现搜索和8次详情。网页默认先做目的地吃法、分片区餐饮及主要门店核验，不为每餐重复同主题搜索。具体缺口可追加并记录原因；只读一两篇综合攻略不能代表所有餐窗已有证据。不要为满足固定篇数重复搜索；原文日期未知就标未知，不伪造近期日期。

## 四个逻辑阶段

1. 根据游玩和吃法候选共同生成 meal_slots：日期、餐别、时间窗、前后具体地址锚点、方式、最大绕行、用餐时长、预算与饮食/停车限制。
2. restaurant-discovery 输出实体、动态快照、meal_candidate_sets。正常每餐两个候选，不提前排序；受限场景提供搜索范围、证据和应急补给。
3. route-data-meals 为每餐提供唯一 baseline，为每个候选计算“上一锚点→门店→下一锚点”。精算或有依据的区间估算都可用，同口径比较。
4. restaurant-ranking 只从同一候选集合给出 meal_options、连续排名、主推备选、用户适配、取舍与切换条件。

默认同一 Agent 完成，不自动增加智能体。分阶段归档但不重复查询；依赖 complete 后才创建后续任务。新任务写 restaurant_research_version=4，详情见多来源契约；旧 v3 任务保留旧规则。

## 数据与候选门槛

- restaurants[] 保存规范名称、具体经营地址、可选坐标/POI、特色菜、饮食限制、合法可视证据和固定入口。没有 POI 时 location.verification 核验经营地址；取得 POI 必须绑定实际地图来源。GCJ-02 与 WGS84 不混用。
- restaurant_snapshots[] 使用 v2 保存适用日期/餐窗、营业、人均、预约排队停车、有效期、复核入口与 evidence[]。身份、菜单、经营及体验分别有来源；平台评分和社区是可选补充，不要求固定小红书篇数。零亲历资料不写口碑共识，保留 partial 和局限；不同渠道读取同文不重复加权。
- meal_options[] 保存约束、候选引用、主备排序、选择理由和切换规则，不能复制地址、菜品、营业等实体事实。普通餐窗主备均须可定位，片区名称不是经营点。
- meal_baseline_routes[] 与 meal_route_evaluations[] 使用一致端点、方式、策略和出发时间。门到门包含进出、停车步行与缓冲，估算明确依据、区间和缓冲并按上界排程；双腿之和减直达基准得到额外绕行。超过 max_detour_minutes 的门店不能保留为主推或备选。

选择先排除饮食、预算、经营和路线不合格者，再比较特色与用户偏好、时间代价、出餐、停车、独立体验与证据充分性。不对工具可用性加分，不把地图结果顺序写成官方推荐，不用互动数当评分，不合并不同评分量表。无评分可继续推荐，理由必须由实际资料支持。路线前地方菜主题不是具体门店评价，菜单核对后才说明主题吻合；同一证据不重复加分。

## 街区逛吃

使用独立 type=food_walk 事件，不把整条街伪装成餐厅。记录 meal_type、具体入口/出口和地图或路线资料、1至4种在该片区有来源的食物、人均预算、实际时间、天气/未营业/拥挤备选。承担午晚餐时至少两种有足够食物量的吃法。自驾定位停车与步行入口，不沿摊位开车逐店跳转。露天不代表允许宠物，按真实限制记录。未核摊位明确为线索，不能把城市菜名推断为该处有售。

固定地点的室内简餐使用普通区域餐窗 `type=meal + mode=area`；街区边走边尝才使用 `food_walk`。因天气或营业风险把室内备选提升为主方案后，必须同步调整事件类型和数据模型。主备方案按动作区别，不要求地址不同；同一商场内换店可以是备选，但须写明“原店未营业/等位过久”等触发条件及换店安排。

新备选按行程契约填写 `name`、`physical_address`、`plan`，不得复制地图响应对象作为游客文案。高德营业字段只代表对应 POI 的平台记录，不自动推断整条街、全部摊位或商场餐饮均关闭。采用时保留查询参数和实际字段依据；缺原始响应时标明归档局限并复核。平台记录、规划者据此做出的取舍与现场待确认事项分开描述。

服务区、封闭景区、机场或深夜确实不足两个商户，可 constrained，但要给可执行补给与复核入口。新契约 meal_exemptions 必须结构化；“酒店附近自选”“菜单待核”属于未完成研究。

## 页面与图片

沿用现有水彩页面：主推显示特色菜、人均参考、地址、营业、到店耗时、操作入口；备选默认收起。双腿路线、估算状态、平台评分和真实证据保留在详情。可用来源就显示实际名称与原文链接，不将公开攻略标成小红书；无高德链接不生成虚假的高德 POI。保留附近搜索作为自由选择入口，不作为推荐证据。

图片来自用户、商家明确允许素材或开放许可，记录作者/机构、原页面、许可和替代文本。无合法图片用原页面/地图/社区的 link_preview；看过社区图片不等于有展示许可。AI 食物图标为非实拍，不能证明门店菜品。完整资料版继续保留全部证据与备选。

## 审查

先验证来源、身份、餐窗与路线，再检查推荐价值。每餐必须能回答实际吃法、具体地点、时间、预算、适配理由与失败切换；不为填两家凑无关门店。影响采用的营业、预约和同行限制未解决时补查或换候选，不能只写“待确认”。旧 v3 的主推3篇/备选2篇门槛只用于旧数据兼容；新标准是结论获得合适、独立且足够的证据。
