# 信息获取与核验策略

查询设计统一遵循[跨渠道搜索设计](search-design.md)：开放发现 → 具体对象 → 执行条件，网页、小红书与高德按各自工具语义表达问题。以下来源优先级用于核验已发现内容，不能把开放发现全部变成官方规则查询。

## 获取顺序

1. 先列出本次研究问题，主动用宿主网页搜索发现并阅读公开原页面；小红书和高德可用时也执行。按问题补充社区、地图与其他可用来源，官方 API 或 MCP 在获取相同硬事实时优先。
2. 优先读取无需登录的公开页面。公开结果缺少必要字段或必须交互选择日期、城市时，才使用浏览器或用户会话。
3. 需要登录时只使用环境允许的认证流程，由用户本人完成扫码、验证码或账号操作。不得绕过风控、频率限制或付费墙。
4. 每次查询记录 `source_id`、原始来源类型、获取渠道 `acquisition`、原页面读取状态 `accessed`、发布者、标题、URL、查询条件、查询时间、适用日期和得到的关键字段，并按[行程研究工作区](research-workspace.md)归档。
5. 自动查询失败时停止重复尝试，转为可执行的手动入口。旧缓存、搜索摘要和历史 workspace 只能用于发现线索，不能冒充本次实时结果。

## 来源分工

| 来源 | 可确认 | 不应单独确认 |
| --- | --- | --- |
| 景区官网、官方微信公众号、文旅部门 | 开放、停止入场、门票、预约、入口和临时公告；公众号身份需由官网、政府页或公众号官方文章交叉确认 | 实际拥挤度、拍照效果 |
| 交通运营方、12306 | 车站、时刻、规则、席别价格和查询时状态 | 未来持续余票、门到门接驳 |
| 酒旅与包车平台 | 候选、查询时报价、服务范围和辅助比价 | 长期库存、最终承运规则、未核验司机资质 |
| 地图平台 | POI、坐标、入口定位、路线、距离和实时路况 | 景区内部开放政策 |
| 商家公开菜单与门店页面、地图门店详情 | 分店、营业、人均、菜单、评分与评价量 | 永久价格、评分和等位时间 |
| 公开亲历游记、社区正文、图片与评论（含小红书） | 当季体验、昼夜效果、地方小吃、街区、口味份量、排队服务、避坑和实测耗时 | 官方价格、营业承诺、开放政策、资质和安全规则 |
| 官方气象机构、可靠天气服务 | 近期预报、预警和历史气候 | 超出可靠窗口的精确天气 |

公开攻略、地方文旅介绍、媒体与商家页面可以发现玩法、菜品及门店；官方宣传不等于独立亲历体验。详见[多来源研究契约](multi-source-research.md)。

## 工具与供应商边界

- 已配置的 `$flyai`、`$variflight`、`$amap-maps` 和 `$xiaohongshu` 可在路线确认后的只读研究中直接使用；路线确认前只允许 `$xiaohongshu` 执行有上限的目的地玩法与美食主题预研。具体工具、参数、安装和登录遵循对应供应商 Skill。
- 餐饮候选可从网上公开页面、社区和地图发现，交叉核对具体分店、菜品、营业与路线；不强制小红书先于其他来源，也不排除文旅介绍提供地方风味线索。公开网页读取遵守访问与证据边界。
- 新增供应商、安装新工具、配置新付费凭证或执行写操作前，检查授权、许可证、维护状态、外发数据、费用、限额和失败行为，并取得用户明确同意。
- 不启用未获授权的私有接口、验证码绕过、网页抓取、轮换 UA/IP、住宅代理或隐藏自动化。不得猜测平台详情 URL。
- 中国铁路最终回到 12306；聚合平台结果不能替代出票前复核。境外铁路回到相应运营方。

## 手动查询降级

必要字段无法自动取得时：

1. 标记 `to_recheck`，写明缺失字段和失败原因。
2. 在 `action_links[]` 中使用真实的官方页、平台搜索页或地图查询页，不拼接详情深链。
3. 链接标签写出日期、地点、站点、人数、席别或房间等查询条件。
4. 记录待复核字段和建议复核时间；用户未回传结果前继续保持待复核。

常用固定入口包括 [12306](https://www.12306.cn/index/)、[携程](https://www.ctrip.com/)、[高德地图](https://ditu.amap.com/)、[中国天气网](https://www.weather.com.cn/)和[中央气象台预警](https://www.nmc.cn/publish/alarm.html)。景区必须使用本次实际定位的官网、公告或当地文旅入口。

## 社区体验研究

- 小红书工具操作及图片笔记读取遵循 `$xiaohongshu`，旅行研究默认只读。发布、互动、删除 Cookie 等状态变更只有用户明确要求时才能执行。
- 临时令牌只用于当前查询链，不得写入 workspace、JSON、HTML、日志或回答。遇到验证码、设备验证或风控立即停止，由用户处理。
- 路线确认前的轻量预研只形成路线取舍、避坑和地方美食主题，不形成具体门店结论；路线确认后的门店研究不得把前置样本重复计入门店口碑。
- 先开放发现推荐；只有已发现的玩法确实受季节影响时，才补“地点 + 月份或季节”，不将这些条件默认塞进首轮；昼夜体验加入日出、日落或夜景；入口加入具体门名；偏远交通加入包车、路况、行李、加价和避坑。
- 每个会影响行程的体验判断尽量交叉不同作者的近期内容，记录发布时间、一致、冲突和疑似推广。新契约按问题相关性、适用性、独立性和证据充分性判断；形成共识需至少两份独立原始体验证据，普通推荐可依据单一可靠资料并明确局限；样本较少时标记 partial、low 并说明不足（旧餐厅 v3 篇数门槛仅用于旧数据），不为凑数量重复搜索。具体次数与复用遵循餐饮研究的预算；无法核对原帖日期时不计入近12个月证据。
- 已读小红书详情必须同时研究评论讨论；默认目标20条一级评论并展开回复，按[评论研究闭环](xhs-comment-research.md)保存实际统计与语义决策。正文质量差仍读评论，不能只摘正文；超阈值的高回复争议保留缺口并按重要性补查。
- `xhs-detail` 的评论洞察层按“相关性 30% + 时效性 25% + 具体程度 20% + 亲历信号 15% + 互动 10%”筛选；泛泛表达、纯求问、推广、重复复制或缺少事实的评论不进入规则候选；反问纠错和有上下文的回答仍保留。规则只作候选，Agent 阅读问答及反向观点后再裁决。最新评论优先用于发现变化，高点赞和高回复只作为传播信号。
- 评论洞察按入口路线、开放施工、预约购票、价格、交通停车、排队拥挤、天气、餐厅体验和特殊人群等主题归并；同主题出现相反预约、开放、拥挤、价格或入口建议时，必须标记冲突。`comment_insights` 的社区置信度最高为 `medium`，冲突或单条证据为 `low`。
- `needs_recheck` 中的开放、营业、价格、预约、交通规则、天气和安全相关结论必须回到官方或实时来源确认；评论只能说明近期体验，不能单独证明当前规则。
- 社区结论最高为 `medium` 置信度。互动数是传播信号，不是餐厅评分；社区内容不能证明当日营业、菜单价、道路管制或司机资质。
- 自动能力不可用时，记录精确查询词、失败原因、小红书入口和复核时间，不用搜索引擎摘要冒充原帖内容。

## 交通平台复核

- 查询绑定具体日期、出发和到达城市或站点，并记录查询时间。
- 携程等平台上的大巴、包车和接驳候选继续核对客运站、承运方、上下车点、行李、报价包含项和退改；能取得官方来源时补充官方来源。
- 12306 无法访问时保留待核字段和用户可执行的查询步骤，不用第三方旧数据代替。

## 置信度与冲突

- `high`：官方来源直接支持，适用日期明确。
- `medium`：多个近期平台或社区来源一致，但没有官方直接确认。
- `low`：来源较旧、单一或互相冲突，只能作为候选。
- 来源冲突时优先适用日期明确且更新较新的官方信息；无法解决时记录差异、取舍依据和复核动作，不静默选择。
