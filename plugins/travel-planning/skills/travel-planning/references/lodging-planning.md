# 住宿区域规划

默认推荐住宿区域范围和大概位置，具体酒店由用户选择。选择区域以当天玩法、美食、次日出发方向、移动成本和连住便利为依据，复用已读攻略和地图信息；只补会改变区域选择的地理缺口，不为填满住宿字段逐家搜酒店。

## 默认输出

- 每晚对应的城市、片区或街道范围，大概位置用公开地标表达；说明连住或换区域的理由。区域不要宽泛到“市中心附近”，也不要缩到未经选择的一家酒店。
- 入住、离开日期与夜数，区域适配理由；必要时给一个不同取舍的备选区域，不强制搜多个候选。
- 有预算时预留住宿费用，写明每间每晚区间、房间数假设和预留依据；这是预算分配，不是酒店市场报价或库存。计入事件费用时使用 estimated，完整入住段只计一次，跨日重复住宿事件不重复收费。
- 选酒店时需要确认的少量条件，例如停车、隔音、电梯、早餐、取消规则；电车行程区分周边公共补能与酒店自有充电，不能从区域条件推断酒店设施。
- 区域路线按代表地标估算，说明覆盖范围、区间与缓冲。实际酒店地址未定时不承诺酒店到景点的精确耗时，不要求房态或供应商预检。餐窗锚点可使用具名公开地标的可追溯地址，不能伪造酒店地址。

地区适配依据保留来源；预算分配、选店条件与待选酒店状态不伪装成已核验事实。用户选定酒店后按地址更新受影响的交通和餐饮衔接。凌晨到达、搬运行李或末班交通确实依赖酒店服务时，明确需要用户确认的条件并留缓冲或有依据的替代方案，不能暗示有寄存或提前入住服务。

## 按需酒店流程

用户明确要求比较或推荐具体酒店时，才调用酒店搜索、报价、地图消歧及必要评论或图片研究；`brief.lodging_mode=hotel` 记录该选择。默认为 area，路线确认不等于开启酒店比选。用户已订或已选酒店时，复用给定地址，不再查询替代酒店或房价；只有相关服务会影响执行时补核。

酒店工具提供候选、位置和查询时的报价，不能仅凭总评分或简短评价声称完成环境与评论区比较。没有读取相关原文和图片时直说信息缺口。供应商预检仅针对这次需要的产品，不因插件具有酒店能力而在每次行程启用。

## 数据契约

沿用 `planning.lodging_options[]` 与事件 `lodging_id`，新增 `kind=area`；具体酒店使用 kind=hotel，缺 kind 的旧记录仍按旧结构读取。区域对象遵守 [lodging-area.schema.json](../schemas/lodging-area.schema.json)：

```json
{
  "id": "stay-central-area", "kind": "area", "name": "市区住宿区域",
  "area": "已研究的街道范围及大概位置", "why_here": "与当晚餐饮及次日出发方向衔接，减少换住",
  "check_in": "2026-10-15", "check_out": "2026-10-19", "nights": 4,
  "location": {"address": "区域内已研究的公开代表地标", "precision": "area"},
  "budget": {"status": "estimated", "currency": "CNY", "nightly_range": [250, 350], "rooms": 1, "basis": "按本次总预算预留，暂按一间房计算"},
  "selection_notes": ["选店时确认停车条件"],
  "route_note": "交通按区域代表地标估算并留缓冲，选定酒店后按实际地址调整",
  "source_ids": ["main-area-guide"], "action_links": []
}
```

字段中的地名、范围和来源必须来自本次研究，示例不是固定预算或城市模板。区域对象不保存酒店库存、房型、供应商报价和已核验酒店身份；可选地图入口标为“查看住宿区域”，不写“酒店导航/预订”。坐标若取得，只表示公开地标并声明坐标系，不表示整个区域或具体酒店。

页面概览、每日详情和随身打印都显示“住宿区域”“预算预留”“选店条件”和区域路线说明。酒店未选不阻断区域规划完成，也不把未选酒店渲染为资料缺失；真正影响到达、行李或安全的条件仍须落实。
