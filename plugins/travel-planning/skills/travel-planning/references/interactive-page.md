# 交互页面规范

最终页面面向普通游客，默认展示整趟旅行玩什么、吃什么，再查看逐日概览、时间轴与出发准备。完整行程表、停靠顺序、备选和来源保留为按需展开的资料。

## 默认视觉设计与模板复用

默认使用“水彩旅行手账”：暖米白纸底、深青绿色正文、锈红批注、宋体标题和少量纸胶带拼贴。手机以单列封面、日期路线票、体验明信片和两列食物贴纸阅读；桌面共用 1224px 容器，路线票最多五列，长行程自然换行。任意目的地与天数复用，不固化宜昌、五天、自驾、慢游或连住条件。

首屏必须有实际生成并标注的水彩封面。首页路线票只表达已审查的日期、日主题和顺序，不能冒充导航地图；体验明信片保留具体条件和日期入口；食物贴纸只绑定研究里真实存在的食物/门店线索，括号里的候选、来源限制与待核状态不可删。每日行程可复用对应日期的插画作明信片摘要；景点内部执行卡保留原有时间、预约、入口、费用与降级方案。行前检查来自 `planning.readiness`，不能凭图标添加无来源的装备清单。

生图与审核遵循[视觉叙事与生图](visual-storytelling.md)。`scripts/render_itinerary.py` 接收 `--visuals` 清单，内联 `assets/frontend/itinerary-app.css` 与 `itinerary-app.js`，同一位图通过静态 SVG symbol 去重；图片库位于 Vue 挂载区域之外，无脚本也显示。真实授权事件图片继续保留作者、许可和原始文件页。生图失败的草稿可降级为可读页面，但不得声称完成标准图文交付。

维护 UI 时修改 `web/src/notebook.css`（手账视觉）、`web/src/style.css`（既有基础规则）、`web/src/App.vue`（视图交互）或 `scripts/render_itinerary.py`（静态结构），在插件 `web/` 运行 `npm run build` 后同步编译资源并重新渲染。普通行程生成不依赖 `designs/`、某份旧行程 HTML、截图或现场 Node.js 构建。图片作为本次行程输入，不把宜昌素材写进插件默认资源。

## 顶部与全局

- 顶部用旅行图片或抽象画面与带字段名的旅行信息组成封面，展示标题、目的地、日期、同行安排和预算策略；缺少的字段直接省略，最后核验时间保留在页脚。手机上图片在前、介绍在后，不复制逐景点费用、逐段交通和逐日天气。
- 顶部提供“玩什么·吃什么 / 全程概览 / 每日行程 / 出发准备”切换，默认进入“玩什么·吃什么”。切换是即时、可逆的页内状态，支持 `Tab` 与左右方向键，不改写行程数据。
- 交互层由 `web/` 中的 Vue 源码经 Vite 编译，产物 CSS 与 JavaScript 由渲染器内联进最终 HTML；旅行者最终仍只收到一份 `itinerary.html`，不得依赖同目录下的本地脚本或样式文件。
- 页面采用渐进增强：Vue 成功挂载后以组件 `v-show` 管理四个视图；微信附件预览、内容安全策略或旧内核阻止脚本运行时，顶部控件必须退化为纯 CSS 单选状态并继续真正切换视图，外部地图入口保留 HTTPS 链接。
- 编译目标不得保留可选链等会让旧版微信 WebView 整段脚本解析失败的语法；发布前同时检查编译包语法、无脚本静态内容和微信内 HTTPS 页面。微信附件预览可能完全禁用脚本，不能把框架编译描述成附件内完整交互的保证。
- PC 端的顶部内容、详细行程、一览表、停靠顺序、信息来源和页脚共用同一个居中内容容器与左右留白；切换视图时内容边界不能横向跳动。窄屏沿用独立的紧凑内边距。
- “玩什么·吃什么”先展示日期路线票，再独立归纳整趟旅行的游玩重点与地方风味，不重复完整逐日事件。餐厅仅为候选或营业未核实时保留该状态；缺少用餐安排时明确写待定，不编造门店。全程概览逐日展示主题、起止时间和必要准备，点击当天进入详细时间轴；完整行程表与停靠顺序按需展开。出发准备由预约任务和行前检查派生，按已知期限排序，不编造办理时间或完成状态。会改变当天执行的约束仍放回对应事件。
- 每日行程提供可横向滚动的 D1～Dn 日期导航，默认只展开第一天，切换时展开目标日期并收起其他日期。无脚本时保留原生折叠区，用户逐天展开阅读。日期仍是一级节点，事件时间是二级节点；不使用滚动监听猜测当前日期。
- 标题区提供轻量的文档图标＋“保存 PDF”按钮和至少 44px 的“更多”按钮，避免与阅读标签争夺视觉重点。保存 PDF 展开小面板，默认推荐随身简版，可选完整资料版，并明确随后进入系统打印窗口保存 PDF，不伪装成直接下载。面板支持 Escape、点击外部关闭和焦点恢复。
- 随身简版从原始行程派生：全程概览、全部日期与事件时间、主推餐厅、准确地址、必要费用、关键预约、入出口、最晚离开和失败应对。备选门店只保留可定位的简短信息，完整口碑、路线与候选详情留在完整版。已有或已核验 POI 的 HTTPS 地点链接在本机生成打印二维码，地址和可点击链接继续保留；二维码及地图需要联网，不承诺离线导航。
- 完整资料版展开全部日期、备选、细节和来源。打印结束恢复原视图、日期与展开状态；直接系统打印及无脚本打印默认随身简版，无脚本不展示不能使用的工具按钮。两种版本都必须实际导出检查分页和内容。
- “更多”提供“复制行程链接”“查看分享二维码”“打印随身简版”；二维码操作打开分享窗口：公网正式 HTTPS 页面可复制固定链接、查看和保存二维码；二维码在本机生成并内联，去掉视图 hash 与追踪参数。本地文件、localhost 与 Netlify 部署预览显示尚无正式链接，不生成误导性二维码。支持 Escape 关闭、键盘焦点循环与关闭后焦点归还；窄屏窗口不溢出。打印时隐藏分享窗口。
- 发布快照的“本版生成”时间与行程事实的页脚“最后更新”分开；发布不会重新核验价格、天气等事实。发布及更新操作遵循[手机分享与发布](publishing.md)。

## 时间轴卡片

- 游客可见文字必须从契约允许的文字字段组装，不直接 `str()` 整个对象、数组或供应商响应。用餐备选按“地点（地址）：触发条件与应对安排”显示，网页和随身打印一致；遇到字段类型错误先阻断生成，不把原始字段名、JSON 或 Python 字典展示给游客。

- 时间轴在“每日行程”中按天展示。景点研究、相邻交通、天气影响和费用不能只存在于完整行程表。早餐准备、普通酒店休息、值机和出站缓冲用紧凑行呈现，保留时间与关键说明；公园、街巷等真实体验保留正常卡片。
- 核心信息使用带字段名的定义列表或表格，不能把时长、区域、费用、预约、入口等值直接塞进无标题 Tag/Chip 让读者猜含义。Tag 只可用于“需预约”“可选”“待复核”等辅助状态。
- 选中日期内的执行信息默认展开：开放时间、停止入场、入口、内部游览顺序、交通线路、必要门票与费用、最晚离开和失败备选。费用拆解与报价核验依据可按需展开；不能把关键期限或必要行动藏进研究详情。
- 事件和节点没有真实且可合法复用的图片时省略图片区；封面与游玩故事可使用明确标注的 AI 氛围插画或抽象装饰，不能冒充实景。
- 每张景点图显示来源、作者和许可，并可跳转原始文件页。小红书等社区内容以“近期体验参考”链接卡呈现，显示标题、作者、互动数与用途说明；临时 CDN 封面不作为行程图片热链。
- 景点卡右上角显示一个至少 44×44px 的天气图标按钮，带可读的 `aria-label` 和摘要 tooltip，点击打开该地点天气网站。天气摘要不再占用定义列表的一行；无天气入口时省略图标。
- 景点卡按“标题与时长区域 → 开放与预约 → 景区内怎么玩 → 注意事项”排序。“开放与预约”是一个完整的行前决策区，内部依次展示开放规则、预约行动与入口、票价与费用，不再在景点卡下方重复渲染独立的“预约与抢票”和“费用明细”卡片。预约说明与临时公告共用同一官方 URL 时合并为“官方预约与公告”，不得因链接去重而隐藏预约动作。已核验微信公众号时，在官网与公告旁显示绿色公众号入口：有官方微信预约说明文章时跳转文章，只有公众号名称时复制名称并提示用户去微信内搜索及进入对应菜单；不得构造不可验证的公众号主页链接或嵌入二维码。
- “景区内怎么玩”使用卡片内部的嵌套时间轴。入口信息并入首节点，出口和最晚离开时间并入末节点，不在时间轴上方另起重复卡片。每个节点展示开始/结束时间、名称、必达/可选、动作；只有研究结果真实提供节点看点或讲解时才显示“现场看点”，不使用通用占位文案。适用时再展示从上一点的移动、节点图片、内部交通、途中餐饮、链接和失败备选。
- 节点图片紧邻对应节点，沿用主图的作者、许可和原始页面规则。节点途中补给引用 `meal_options[]`，不把菜品、人均和排队信息重复写成自由文本。
- 景点费用继续区分基础门票、必选景交、可选项目、互斥套票和2人/全体基线小计。
- 交通：精确起终点、线路/车次、门到门时间、费用、换乘、推荐理由和备选。提前规划页面不展示“实时状态”行；需要临行处理的动态条件写成有时间点的复核任务。
- 交通卡只展示准确的导航目的地、可复制的地点名称和一个“在高德打开地点”外链；有已核验 POI ID 时优先打开 POI 详情，没有时使用已核验的地图链接。保留必要的门到门时间、费用、换乘和备选。不得在 HTML 嵌入地图 iframe、登录页、全屏地图或声称网页能替代车机导航。
- 出发时由用户在手机或车机中核对目的地，再用实时导航和现场指引行驶；规划阶段的静态路线、拥堵和车程不能冒充实时信息。
- 住宿默认按[住宿区域规划](lodging-planning.md)展示区域范围、大概位置、入住日期与夜数、选址理由、预算预留、选店条件和区域路线估算；不把未选酒店展示为价格待查询或身份已核验。按需酒店候选再展示报价、实际地址与已核验服务。
- 餐饮：事件标题后展开 `selected_candidate_id` 对应的综合推荐，默认展示特色菜、人均参考、准确位置、营业、到店耗时、已知预约要求和地图入口。`fallback_candidate_ids` 对应的备选默认收起，展开后保持稳定卡宽；简短展示有证据的切换条件。平台评分、小红书原帖或搜索入口、停车和完整前后路线放入原生“查看前后路线与口碑依据”折叠区，不删除完整研究。两段路线仍显示真实的起终点名称、双方地址、距离与门到门时间，并由标题直接链接高德；不能只剩“从上一站”。每卡最多一个规范化高德门店入口，不重复导航别名或事件级门店链接。每餐以上一锚点为中心的附近搜索与主推门店入口放在同一操作区。时间窗不重复展示，不提供内部打分、页内排序和“已选为本餐”等状态。高德评分缺评价量时保留评分并写“评价量未取得”，不合成跨平台总分。
- 小红书存在满足门店身份与时效要求的原帖时，直接展示原帖标题、作者和链接；没有门店级原帖时只提供门店搜索入口，不得展示城市级美食主题分数或将主题笔记描述为门店口碑。所有面向旅行者的平台名统一显示为“高德”和“小红书”，不展示内部 provider ID。
- 风险：天气、高反、拥挤、晚点和临时关闭时的备选。

## 完整行程表（概览底部按需展开）

按[研究深度](research-depth.md)区分餐窗：区域餐在概览、每日详情和随身打印显示具体区域与地址、正餐吃法、预算预留、供给说明与可定位备用，不显示空的门店排名和评分。天气研究的适用日期、季节/预报依据、风险、调整方案与复核时间进入出发准备及随身打印；同日期事件共用天气对象，不复制天气事实。

- 一览视图使用小字号、紧凑行高和表格线，固定为“时间 / 地点 / 关键信息”三列，日期作为跨列分组行，不再复制图片、地图、来源、操作按钮和研究字段。
- 第三列按事件类型选择会改变执行的信息：景点展示特色、游览顺序、开放、进出口、最晚离开、预约、费用和备选；交通展示方式、线路、门到门耗时、费用和备选；餐饮只展示综合推荐门店、特色、菜系、人均、营业和绕行，不重复选择理由、备选与切换条件；住宿区域展示范围、大概位置、入住夜数、预算预留、选店条件和估算衔接，具体酒店候选再展示报价与服务。
- 窄屏仍保留表格语义，使用带焦点的横向滚动容器查看完整三列，不拆成卡片；打印时移除阴影与粘性表头。

## 完整停靠顺序（概览底部按需展开）

- 按日期展示 `planning.daily_routes[]` 的有序站点列表，不渲染整日高德混合路线。每个停靠点显示编号、地点和有来源的备注；从第二站起可填写 `arrival_mode`（例如自驾、景区巴士、步行），按实际分段方式标注，不知道时省略，不能推断成统一驾车。
- `daily_routes[].stops[]` 按当天实际事件顺序列出住宿出发点、景点、主选正餐、其他停靠点和结束点。没有足够站点时显示明确空状态。
- 逐段的准确目的地和高德外链在详细行程交通卡中提供。停靠顺序只帮助理解当天安排，不承担导航职责。

## 操作按钮

每个按钮由 `action_links[]` 生成：

- `map`：地图定位或导航。
- `official`：景点/酒店/餐厅/承运方官网。
- `official_homepage`、`official_notice`、`official_booking`、`official_wechat`：景点官网、公告、网页预约和微信公众号预约说明入口，四者不可混用。
- `weather`、`weather_warning`：地点天气页和官方预警页。
- `ticket`：景点购票页。
- `train`：铁路查询/购票入口。
- `bus`：大巴查询/购票入口。
- `hotel`：酒店详情/预订入口。
- `restaurant`：餐厅详情/预约入口。
- `guide`、`image_source`：节点讲解和图片原始页面。
- `source`：查看支撑当前结论的信息来源。

按钮必须展示平台名。外部跳转统一新窗口打开并使用安全链接属性。价格标明估算、平台候选或已确认；查询时间与有效期保留在同卡可展开的核验依据中，最终以平台为准。页面只负责跳转；没有用户单独明确授权时，不自动选座、填乘客、提交订单或付款。

已核验高德 POI 的餐厅卡提供一个“在高德查看门店”入口；交通卡提供一个目标地点入口。移动端是否调起高德 App 由设备和浏览器决定，不能保证。高德链接用于用户实时查看和自由选择，不代表高德为本行程背书。

## 汇总与派生

- 预算：从事件 `cost_items[]` 派生交通、住宿、门票、付费项目和餐饮小计；区分已确认、平台价、估算、待复核和可选。汇总可以放在行程末尾，但不能维护第二套金额。
- 待办：购票、订房、景点预约、餐厅预约及各自截止时间。
- 每日强度：步行、爬升、换乘次数、最早出发、最晚回酒店。
- 复核提醒：天气、余票、价格、开放时间和临时公告的再次检查时间。

## 游客编辑与状态

- 概览、每日详情、出发准备都从同一份研究和事件数据派生；不新增脱节的摘要事实或预算。概览优先突出每天明确的游玩和餐饮选择，同时如实标注候选与待定，不要求用户重新研究所有候选。
- 不按 `rest` 类型统一弱化活动；只有普通准备、休息与缓冲采用紧凑行。压缩不删时间、警告、预约或缓冲。
