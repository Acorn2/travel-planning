# 标准规划流水线

整条流程为“多来源轻量预研 → 路线确认 → 预检与采集 → 共享状态合并 → 编排 → 审查 → 交付”。阶段通过文件和门槛连接，不在采集过程中边查边写最终页面。

## 0. 建档与路线确认

1. 创建唯一的 `.travel-research/<trip-id>/` workspace，保存 `brief.json`。
   按[调用范围与执行效率](execution-efficiency.md)在预研开始前记录 discovery 阶段，阶段结束及时关闭。进入路线确认等待时单列 waiting_for_user，用户回复后结束等待，不计为研究耗时。
2. 按[跨渠道搜索设计](search-design.md)先用“目的地旅游推荐”“目的地美食推荐”发现玩法与吃法，读正文、图片和评论后形成候选，再按兴趣、天数和节奏组合路线；天数不默认带入小红书关键词。用宿主网页搜索读取公开资料，按需补充可用的小红书或地图，完成路线前轻量预研并保存 `route-context.json`；辅助工具不可用时继续网页研究，网页也不可用时记录具体失败与查询建议。
3. `route-context.json` 保存逐次查询记录、公开原帖引用、路线/时段/避坑信号、地方美食主题、冲突和置信度。新记录使用 `query_design_version=1`，含真实平台、工具、非敏感参数、问题、阶段和结果取舍；路线确认后继续保留并合入最终研究契约，不能丢掉预研或把多次查询压成一句话。不得保存临时令牌，不得把社区说法写成营业、价格、开放或安全事实。
4. 结合 brief 与社区上下文生成 `route-proposals.json`。每个方案说明受哪些社区信号影响；未采用的信号及理由也要保留，避免把热度直接等同于适合本次行程。
5. 用户确认后写入 `selected-route.json`。确认前不得扩展为逐景点、逐门店或库存价格研究。

进入下一阶段前，日期、出发地、人数和路线方向必须确定；这些输入变化时更新版本并使受影响的旧任务失效。

## 1. 预检与前置采集

先按[研究深度](research-depth.md)记录交通、餐饮和天气的 basic/detailed、决策因素及理由，新计划使用 research_depth_version=1。普通餐可用区域餐窗；重要餐用门店三阶段。交通只比较相关维度，天气按地域日期与活动敏感度研究，不把所有对象都扩展为详细研究。

先检查宿主网页搜索与读取能力，再按[实时数据工具](live-data-tools.md)明确选定需要的供应商，或直接执行实际业务查询；复用有效运行与查询记录，不默认探测全部来源。小红书、高德不加入供应商 `--require`；工具齐全仍执行网页研究。新工作区仍启用单独的小红书详情采样配额，工具失败可继续其他研究，但未达配额时 final 审计阻断。不能通过供应商预检推断宿主搜索状态。研究开始/结束记录 research（或所需领域）阶段，包装命令用 --phase 对齐该阶段。

默认由主 Agent 按逻辑阶段研究；确需委派时才按[子 Agent 编排](agent-orchestration.md)确定任务域、依赖和字段所有权。需要目录、归档或提交命令时再读[行程研究工作区](research-workspace.md)。子 Agent 只产出规范化实体、共享实体、快照引用、事件绑定、约束和未解决项，不写完整行程或长篇调研报告。

采集内容按领域完成：

- 景点、出入口、内部 checkpoints 和交通边遵循[景点与路线研究](research-workflow.md)。
- 正餐候选、小吃街与夜市、动态信号和双向绕行遵循[餐厅候选研究与路线适配](restaurant-research.md)，按用户偏好同时安排玩与吃，先确认饮食体验再与景点共同排片区。
- 住宿按[住宿区域规划](lodging-planning.md)复用已研究的区域信息，默认给范围、代表地标、入住日期与夜数、理由及预算预留；用户明确要求酒店比选时才查酒店供应商、房型和报价。
- 节假日、行李、特殊人群、入境与分阶段复核遵循[行前就绪检查](trip-readiness.md)。
- 来源等级、冲突和自动查询失败遵循[信息获取与核验策略](source-strategy.md)。

采集完成门槛：

- 拟采用景点有适用日期的开放与预约、可定位入口和出口、内部卡点、费用及最晚离开时间。
- 每段移动有稳定 `route_id`、精确起终点、门到门时间、费用、行李、备选和动态状态。
- 完整旅行日有实际午餐和晚餐时间窗。普通区域餐窗有具体地址、正餐吃法、供给来源、预算与可定位的备用补给；detailed 餐窗保留主备实体、动态运营证据和同口径路线。承担正餐的 food_walk 按逛吃规则验证，不能用区域名或“附近自选”填空。
- 动态价格、库存和运行状态已经落入 `snapshots/<task_id>/`，采用候选通过 `inventory_refs[]` 绑定具体 offer。
- 住宿区域可定位，入住日期与夜数一致，预算属于预留，相关交通按区域估算；无需具体酒店、房型或库存即可完成区域方案。按需采用酒店报价时才核验身份、人数、房间、床型与库存口径。
- 所有任务结果、来源和证据已经提交到 workspace，不只存在于 Agent 上下文。
- `research_contract.version=1` 记录实际网页研究（辅助工具齐全也需执行）、渠道状态、查询及来源；采用的主要玩法与主推餐厅有用户价值、取舍和具体证据，冲突有裁决。不能按某个工具是否可用判断整趟研究完整度。

## 2. 主 Agent 编排

阶段边界记录 planning 计时；合并与装配命令另自动记录其执行时间，不能相加为总耗时。

本阶段默认不重新浏览。先校验任务状态、输入版本、字段所有权和来源，再按稳定 ID 合并：

1. 运行 `merge` 重新校验任务结果，并按稳定 ID 生成景点、交通枢纽、住宿和餐厅的 canonical entity registry；从任务索引按需读取完整结果。
2. 汇入标准快照，锁定预约场次、航班或车次、停止入场、日出日落和末班交通等硬时间。
3. 生成只含硬时间、门到门交通、餐窗和最晚离开的候选事件流，立即执行时间空间预审。
4. 冲突时先重排，再按“换交通方式 → 缩短次要景点 → 取消次要活动”降级；必要时创建 `gap-*` 修补任务。
5. 插入住宿、行李、正餐和休息，将天气、费用与预约通过稳定 ID 注入对应事件或 checkpoint。
6. 将字段冲突的采用值、理由和来源写入 `state/merge-decisions.json`；将选用实体、逐日事件、时间窗和降级策略写入 `state/itinerary-plan.json`，不得为单次行程生成 Python 装配脚本。
7. 使用通用装配器校验计划绑定的 `research_state_sha256`，再生成 `artifacts/itinerary.json`。预算只由事件费用派生。

装配前按[多来源研究契约](multi-source-research.md)逐项复核采用的玩法、主推／备选餐厅、街区食物与执行条件。判断原页面是否实际读取、证据是否支持推荐、是否转载重复、适用日期与冲突，而非统计某个平台篇数。新计划必须显式写 `planning.research_contract`；餐厅使用 v4 契约与 v2 快照。旧数据保持可读，修改后按新流程补研究，不自动迁移为已核验。


```bash
python3 skills/travel-planning/scripts/assemble_itinerary.py \
  --workspace ".travel-research/hangzhou-2026-10"
```

研究状态重新 `merge` 后摘要会变化，旧计划必须停止装配；先重新完成受影响的路线决策，再更新计划中的 `research_state_sha256`。可用 `--print-research-sha256` 读取当前摘要。

事件卡只保留会改变时间、地点、动作、费用或备选的信息，不放目的地百科、泛化提醒、研究过程或重复来源说明。

## 3. 独立审查

先在硬时间事件流完成后检查时间与交通，再在动态候选绑定后运行最终确定性审查；主 Agent 检查事实冲突和语义可执行性，确需独立复核或用户要求时才委派。

审查至少覆盖：

- ID、引用、来源、查询时间、快照与 offer 绑定是否完整。
- 查询是否按[跨渠道搜索设计](search-design.md)先开放发现吃与玩、再依据实际结果逐步缩小范围；旅行天数用于筛选和排程，不默认带入小红书关键词；是否把多个预设对象拼成发现词、只查官方规则就声称完成发现，或将少量结果误判为当地选择少。核对实际工具输入、不同作者原文、未采用理由与剩余缺口，不以自动通过或查询次数替代内容判断。
- 停止入场、用餐、入住退房、行李、交通缓冲和相邻路线是否可行。
- 官方事实是否被社区信息覆盖，动态结果是否被写成未来承诺。
- 用户价值：体验是否具体、符合用户兴趣与同行限制、避免重复，是否值得时间、费用和体力；推荐与首页亮点是否绑定实际事件或明确标为未采用线索。
- 页面能否直接回答入口、内部顺序、费用、抢票、餐饮、地图和失败备选；缺餐豁免须是有证据和可执行补给的受限场景。

审查写入 `state/audit.json`。只有 `blocking=[]` 才能渲染最终 HTML；warning 只保留当前阶段无法消除的动态复核事项，并附时间和入口。

## 4. 交付

分别记录 visuals 和 delivery 阶段，审查/渲染命令自动记录；结束后生成 state/execution-report.json，检查未结束阶段、慢调用和复用情况。报告只覆盖已记录执行，不给未实测步骤估算耗时。

事实与语义审查通过后，按[视觉叙事与生图](visual-storytelling.md)生成、查看并归档本次行程的水彩图片及清单。标准交付须有实际位图；生成失败说明草稿缺口，不用纯文本替代完成状态。读取[交互页面规范](interactive-page.md)，使用本 Skill 的 `scripts/render_itinerary.py` 和随插件交付的编译资源生成默认“水彩旅行手账”UI，不为单次行程另写页面模板。运行渲染器后检查手机和桌面、外部地点入口、无脚本视图切换、外部链接、图片失败和打印版。交付 `itinerary.json`、`itinerary.html`、审查结果和少量必须由用户处理的预约或复核动作。

每次新增或修改行程，先交付 `travel-plans/<trip-id>/index.html` 的绝对路径链接，说明“本地待审核，尚未发布”，等待用户审核 HTML。用户需要手机分享时，可按[手机分享与发布](publishing.md)在本地准备快照；只有用户明确确认发布当前审核版本后，由 Agent 完成发布与匿名核验，不要求用户执行 Python。历史自动发布授权、路线确认或 Token 配置不能替代本次确认；内容再修改须重新审核确认。配置从项目根目录 `.env` 读取。更新复用站点和行程路径；生成 HTML 不等于已经上线。

## 扩展接口

新增 Agent 或数据源不得直接改最终行程。它必须声明输入与依赖路径、拥有和禁止写入的路径、字段所有权、规范化产出、完成门槛、失败状态和复核时效；主 Agent 继续按相同合并和审查流程处理。
