# 旅行规划

将旅行需求转化为可执行的逐日事件流，并交付可独立打开的响应式 HTML 页面和对应 JSON。

## 恢复已有行程时先核对观察

复用已有 workspace、重新规划相同行程，或用户追问小红书是否可用时，先运行 `python3 skills/travel-planning/scripts/research_sources.py xhs-state --workspace <工作区>`，读取各主题的最新搜索与实际详情/评论观察；该命令只读本地证据，不证明服务当前在线。不要只读取 `route-context.json`、旧方案或旧回复中的失败总结。

历史失败不能充当本轮调用，不能因“之前已重试”跳过修复、换端点或隔轮后的首次查询。需要的主题只有历史失败且没有可用证据时，按当前包装器重新查询；明确复核或修复后用 `xhs-discover --refresh`，仍遵守每次最多两次搜索及验证/限流立即停止。当前失败不叠加同词重试。成功结果按有效期复用，已读原帖按问题与时效复用，不为刷新状态机械重读所有帖子。

分三步验收：搜索列表成功 → 选样读取正文/必要图片 → 实际取得评论与回复。只拿到列表不能说已读笔记，未调用详情不能说评论抓取失败。回答“这次尝试过”必须对应本轮调用或明确标注复用的原时间；没有新调用就说“本轮未重新查询，旧失败不代表当前状态”。旧失败保留为历史，新的成功观察与研究摘要同时归档，不能继续把旧失败当作当前汇总。

## HTML 审核与发布门槛

每次新增或修改行程，默认交付本地 HTML 供用户审核，不自动发布到 Netlify。事实/语义审查与页面验证通过后，给出 `travel-plans/<trip-id>/index.html` 的绝对路径链接，说明“本地待审核，尚未发布；审核满意后可回复‘确认发布’”。只有用户看过本次 HTML 并明确确认发布当前版本，才可调用 `publish_itinerary.py publish --confirm-public`。

路线确认、规划开始前的分享需求、已有 Token/站点配置、之前行程的发布同意或历史自动发布授权，都不能替代本次 HTML 的发布确认。只同意内容但未表达发布意图时仍停在本地。用户要求修改则先更新并重新验证本地 HTML，再交付审核；确认后内容再改变须重新确认，不把一次确认用于后续版本。当前版本已获明确发布确认后，由 Agent 完成部署，无需再次索取同一授权或让用户执行命令。

## 路线确认门槛

1. 只收集会显著影响方案的信息：出发地、目的地、日期或天数、人数、预算、节奏、兴趣、住宿位置和硬性限制。除日期、目的地或无障碍安全风险外，缺失信息可用明确的低风险假设补齐。
2. 生成路线方案前，使用宿主网页搜索与原页面阅读做一次有上限的目的地轻量预研，并按需补充已配置且可用的小红书，提取近期反复出现的玩法、时段、避坑和地方美食主题；只把它们作为路线比较上下文，不在此阶段研究或推荐具体门店。来源不可用时记录原因并继续，不为这一步安装工具、要求登录或阻断路线确认。
3. 深度调研前给出 2～3 个路线方案，说明城市顺序、停留天数、主要交通、预算区间、节奏、亮点和风险，并标明哪些取舍受社区体验信号影响。
4. 让用户选择、合并或调整路线。除非用户明确要求“直接按你推荐的做”，否则不得跳过等待确认。
5. 路线确认前不虚构精确车次、余票、库存或实时价格，也不启动逐景点、逐餐厅的大规模研究；上述多来源轻量预研是允许的研究例外。

## 调用与计时

已采用小红书原帖时，交付回复同时汇报实际一级评论、回复、规则有效样本及洞察数量，并说明未读讨论或失败。统计从最终审查的 `community_audit.comment_research` 获取；原帖显示总数、加载目标、重复读取和正文篇数不能冒充评论抓取量。

先按[研究深度](references/research-depth.md)区分普通执行信息与影响核心决策的深入研究。新计划设置 planning.research_depth_version=1，交通、餐窗和天气对象声明 research_depth、depth_reason、decision_factors；核心体验、饮食限制、硬时间及天气敏感因素按实际影响追加研究，不能为省时省掉关键核验。

实际调用前按[调用范围与执行效率](references/execution-efficiency.md)确定所需来源；预检只选择这些来源，不默认探测全部工具。优先复用同一行程中条件一致且仍有效的结果，保留原查询时间，关键条件变化或明确复核时重新查。包装命令传 workspace 和当前 phase；研究、编排、视觉制作与交付记录阶段边界，用户等待单列。结束后生成执行报告，区分工具耗时、复用与阶段时间；未记录的步骤不补造耗时。

## 住宿默认范围

默认按[住宿区域规划](references/lodging-planning.md)推荐区域范围、大概位置、入住夜数和预算预留，具体酒店由用户选择。复用路线与餐饮研究，不默认启动酒店供应商预检、逐家酒店搜索、房型、报价、库存、图片或评论比较。只有用户明确要求具体酒店推荐或比较时才开启；已选酒店直接使用给定地址衔接。区域锚点不是已核验酒店，相关交通保留估算范围和缓冲；酒店未选不阻断区域方案交付。

## 多来源研究基础能力

实际查询前读取[跨渠道搜索设计](references/search-design.md)：先用游客自然表达的攻略、推荐问题发现选择，再研究已发现对象与执行条件。小红书首轮分别用“目的地美食推荐”“目的地旅游推荐”，从正文、图片和评论发现候选后再取舍；默认不加旅行天数，不先定菜品/景点再倒查依据。天数用于排程，具体对象补查须来自用户指定或已读发现。关键词按渠道和单一问题设计，高德附近搜索使用坐标与半径。新工作区使用 `research_contract.query_design_version=1`，逐次记录真实工具输入、平台、目的、阶段和结果取舍，不事后拼接综合关键词代替调用记录。

正式小红书搜索统一走本项目的 `xhs-discover` / `xhs-search` 包装命令，不用直接 MCP 搜索替代；包装代码负责默认参数、最多一次恢复和尝试记录。上游超时或筛选控件失败时先实时复查登录，验证正常后重试一次；失败后不在 Agent 层叠加同词重试。登录失效、验证码、设备验证、风控与限流立即停止。无筛选降级必须保留原条件、实际条件及警告，不能声称原筛选已生效。

新工作区的吃与玩开放发现都完成后，正式研究必须运行 `xhs-sample --workspace <工作区>` 自动按主题顺序读取去重候选，直到每个目的地至少读取15篇独立笔记、吃和玩各至少5篇；候选只来自成功的开放发现，计数只认成功归档的详情与评论，不认搜索列表、重复读取或平台显示的评论总数。登录、验证/风控、限流、连接或详情解析故障立即停止并报告已读数和缺口；最终审计与渲染在配额未达标时阻断，不得标记研究完成。具体采样命令和进度字段见[搜索设计](references/search-design.md)。旧工作区继续按原契约读取，不补造采样历史。

遵循[多来源研究契约](references/multi-source-research.md)。模型知识用于提出候选和待证问题，不作为实时证据。网页搜索与原页面阅读是默认研究路径：**小红书和高德都可用时仍主动搜索公开网页**，不能等待辅助来源失败才搜索。候选可来自公开攻略、官方或商家资料、媒体、社区、地图及用户素材；按事实类型选择核验来源，不强制每个对象查询三个平台。网页、社区与地图围绕同一研究问题相互触发补查；转载与同一原帖的不同读取渠道不能累计成独立共识。

先检查宿主是否提供真实网页搜索和页面读取，再按本次需要对已配置供应商预检。宿主搜索由 Agent 实际调用并记录，`research_sources.py preflight` 仅探测供应商，不能代表宿主搜索不可用。高德、小红书、飞猪和飞常准仍不默认加入 `--require`，未就绪时继续其他可行研究，不自动安装、登录或配置凭证；但新工作区的小红书详情采样版本另有15篇配额门槛，来源故障时路线研究可继续，final 必须保留未达标状态并由审计阻断。

路线确认后可直接执行已配置来源和公开网页的只读查询，确认前只做有上限的目的地预研。中国境内地图优先 `$amap-maps`，社区体验可用 `$xiaohongshu`，酒旅和交通候选按需使用 `$flyai` 与 `$variflight`。无需小红书也可用公开亲历资料支持体验；无需高德 MCP 也可用已读地图网页、官方交通说明和有依据的区间估算规划。精算缺失必须标记估算、保留依据与缓冲，不能伪造 POI、坐标或精确绕行。关键开放、预约、安全或交通条件无法确认时补查或调整安排，不用泛化提醒代替解决。

新行程使用 `planning.research_contract.version=1`，餐厅使用 `restaurant_research_version=4` 和 v2 快照；旧版已存行程仍可读取，但不能声称已按新标准核验。主 Agent 记录渠道可用性、实际查询、采用来源、推荐价值与取舍、冲突裁决和未解决项。网页读取失败、搜索无结果、辅助工具不可用与证据不足是不同状态。所有外部读取均不可用时只能交付明确标记的待核草稿，不作为通过完整研究的最终结果。

## 不可违反的约束

- 对开放时间、临时关闭、票价、库存、班次、天气、签证和交通规则等时效信息，使用适用日期的实时来源，记录 `checked_at` 和网址，并区分官方事实、平台快照、社区体验与估算。
- 景区官网、运营方和政府渠道确认开放、票价、入口和规则；社区内容只支持当季体验、拥挤、玩法、餐厅体感和避坑，不能单独证明营业、价格、资质或安全。
- 自动查询失败时提供真实的官方或平台 HTTPS 入口、查询条件、待核字段和复核时间。不得猜测详情深链，也不得用首页、旧缓存或搜索摘要冒充已核验结果。
- 飞猪和飞常准的完整结果先转换为 `travel-source-snapshot/v1` 并写入任务 `snapshots/`。研究结果只引用 `source_snapshot_ids[]`；采用的交通和住宿候选通过 `inventory_refs[]` 绑定具体 `snapshot_id + offer_id`。供应商原始私有字段不得进入行程层。
- 中国铁路最终回到 12306 复核；平台候选不代表余票、锁价或出票。酒店供应商未校验多间同房型库存时，只能称为报价候选。
- 不输出、归档或传递凭证、Cookie、登录或授权二维码、授权头和临时令牌。行程公开链接的分享二维码按发布规范生成。遇到登录、验证码、设备验证或风控时停止该来源，由用户本人处理。
- 未经用户对具体项目、日期、数量、价格及乘客或入住人确认，不提交订单、付款、发送消息或修改预订。页面中的购买、订房和购票控件只负责跳转。
- 不虚构预订结果、实时价格、库存、开放状态或来源；所有估算明确标记。

## 研究与编排

对拟采用的景点研究适用日期的开放与预约、入口和出口、游览时段、内部 checkpoints、费用、补给和最晚离开时间。交通按出口到下一入口计算门到门时间，包含步行、等候、换乘、安检、取行李和缓冲；跨住宿夜明确行李去向。先按硬时间和地理方向排程，再比较价格。

默认主 Agent 完成研究；天数或来源数量不自动触发委派。用户要求并行，或确有可独立交付且足以减少等待的研究域时，按子 Agent 编排拆分，并说明任务与查询预算；普通单城市自驾不必拆分景点、住宿、餐厅发现、路线和餐厅排序为多个智能体。发现→路线→选择是逻辑阶段，可由同一个 Agent 执行并复用已有结果。子 Agent 只提交 assignment 允许的研究结果、来源、快照和证据；主 Agent 负责路线、合并、冲突裁决、最终 JSON 和页面。

跨 Agent 复用的数据统一写入本次 `.travel-research/<trip-id>/state/research.json`；不建立跨行程缓存。各任务只写自己的结果、来源和快照，`merge` 重新校验后按实体 ID 汇总 `shared_entities[]`，自动合并互补字段、记录冲突，并汇总事件绑定、约束和未解决项。

## 合并与审查

处理结果遵循[行程数据结构](references/itinerary-schema.md)中的字段类型与用餐模型规范。新用餐备选使用结构化地点、地址和应对安排；装配、审查与渲染共用校验，不能把对象或数组直接转换成游客文案。主方案调整后重新检查事件类型及主备动作是否重复；室内区域用餐不套用街区逛吃模板。

前置采集完成后，按稳定 ID 合并为 `itinerary.json`。先生成只含硬时间、门到门交通、餐窗和最晚离开的候选事件流，立即检查时间空间冲突；无法同时满足时按“换交通方式 → 缩短次要景点 → 取消次要活动”降级，不把冲突留成一句提醒。

主 Agent 将选用实体、逐日事件、时间窗和降级策略写入 `state/itinerary-plan.json`，使用通用装配器生成 `artifacts/itinerary.json`；不得为单次行程编写 Python 装配脚本。生成最终页面前必须满足：

- 每个事件有稳定 `id`，并通过 ID 引用相应景点、交通、住宿、餐饮、天气、预约和费用数据。
- 景点事件包含结构化开放与预约信息、入口、出口、内部 checkpoints、最晚离开和费用；官方主页、公告、预约入口与实体地址分开。预约主要在微信公众号完成时，另记录已核验的公众号名称、菜单路径和可用的官方说明文章入口。
- 每个完整旅行日有实际午餐和晚餐安排。普通日常餐可用有来源的区域餐窗：正餐吃法、具体街段与地址、预算预留、供给依据、时间和可定位的备用补给；不逐店排名或计算候选双腿路线。核心特色餐、饮食限制、供给受限和硬时间冲突使用详细餐厅研究，保留主推与备选、运营来源、路线和切换条件。小吃街用 food_walk，可承担正餐；不能以“附近自选”或“待核”豁免。
- 餐饮层只保存餐窗、前后锚点、约束、候选引用、主备决策和切换规则；每个前后锚点必须具有明确名称与具体地址；坐标取得时声明坐标系，未取得时采用有依据的路线估算。地址、菜品、人均、营业等候选事实只保存在餐厅实体与动态快照中，不复制成餐饮摘要字段。
- 交通记录准确起终点、门到门时间、费用、备选、行李和需要复核的动态条件；提前规划页面不展示当前拥堵、排队等实时状态。住宿默认保存 kind=area、区域范围、代表地标、入住日期和夜数、选址理由、预算预留与路线估算说明；用户要求酒店比选时才保存房型、报价与酒店身份核验。
- 天气和预算由被引用的对象或事件派生，不维护另一套脱节的展示数据。未获得的动态字段使用带原因、入口和复核时间的 `to_recheck`，不能裸写“待确认”。

候选事件流完成后检查硬时间与交通，动态候选绑定完成后执行最终确定性审查；主 Agent 再检查事实冲突和语义可执行性，风险确需独立复核或用户要求时才委派审查。阻断项清零后才能渲染最终页面：

```bash
python3 skills/travel-planning/scripts/assemble_itinerary.py --workspace ".travel-research/<trip-id>"
python3 skills/travel-planning/scripts/audit_itinerary.py ".travel-research/<trip-id>/artifacts/itinerary.json" --output ".travel-research/<trip-id>/artifacts/audit.json"
```

## 页面与交付

后续行程默认沿用用户已确认的“水彩旅行手账”：暖米白纸底、水彩封面、沿日期展开的路线叙事、体验明信片与少量美食贴纸拼贴，面向在手机和小红书阅读、收藏攻略的用户。除非用户明确改变设计，复用通用渲染器与编译资源，不为单次行程另写 HTML/CSS。

事实/语义审查通过后、渲染前，读取[视觉叙事与生图](references/visual-storytelling.md)，执行本次行程的图片生成与看图验收。标准交付必须包含实际生成的水彩位图，不能用纯文本、渐变或代码图标替代生图；至少生成封面与一个主要体验场景，有明确食物线索时增加食物插画。原图、提示词与清单保存在本次研究目录，通过 `--visuals` 内联到页面。无生图能力或生成失败时仍可提供可读草稿，但必须说明图片交付尚未完成；用户明确要求纯文字时可例外。图中不写预算、时刻、地址等事实，所有内容从已审查的 JSON 派生；AI 图明确标注非实景/非实拍。

渲染时读取[交互页面规范](references/interactive-page.md)，并执行：

```bash
python3 skills/travel-planning/scripts/render_itinerary.py ".travel-research/<trip-id>/artifacts/itinerary.json" ".travel-research/<trip-id>/artifacts/itinerary.html" --visuals ".travel-research/<trip-id>/visuals/manifest.json"
```

页面面向普通游客，默认提供“玩什么·吃什么 / 全程概览 / 每日行程 / 出发准备”四个入口，首先展示全程日期路线票，再按整趟旅行归纳游玩与餐饮；每张体验和美食卡可进入对应日期。全程概览每个旅行日只展示主题、起止时间与提前准备；点击进入当天时间轴，不把所有事件默认铺满首页。完整三列表格与停靠顺序保留在概览底部，按需展开；旧 `#route-view` 链接仍可进入完整停靠顺序。

每日行程提供 D1～Dn 日期切换，默认只展开第一天，切换时只展开目标日期。无脚本时使用原生日期折叠区逐天阅读。早餐准备、酒店休息、值机与出站缓冲采用紧凑行，但保留时间、必要说明和失败备选；公园喝茶、街巷散步等真实旅行体验不能因类型为 `rest` 而弱化。当天主要路线放在时间轴顶部；完整停靠点仍由 `planning.daily_routes[]` 记录，不推断没有依据的交通方式。

详情默认保留会改变执行的开放规则、预约要求与截止时间、准确入口、最晚离开、必要费用、交通线路、目的地和失败备选。景点的“开放与预约”集中展示相关规则、预约入口与票价，不在卡片下方重复。餐饮先展开一家综合推荐，展示特色菜、人均参考、准确地址、营业、到店耗时和地图入口；备选默认收起，提供简短且有证据的切换条件。完整前后路线、双方地址、距离、平台评分、小红书原帖或搜索入口放在“查看前后路线与口碑依据”中；不要删除证据，也不要默认展示内部打分和计算过程。两段路线标题直接链接高德，每张餐厅卡最多一个门店入口，附近搜索与主推门店入口放在同一操作区。

出发准备从 `booking_tasks[]` 与 `readiness[]` 派生，按已知办理时间和期限排列，保留订票、订房、预约、天气及同行限制。没有精确期限时不编造日期。已核验信息不代表已预订；页面不伪造完成状态，不提供没有持久化能力的任务勾选。将 `to_recheck` 等内部状态翻译成游客能理解的文字，规划耗时使用合理取整的“约几分钟”，精确发车和入场时间保持原值。

渲染前增加一次面向游客的编辑审查：概览能否说明每天怎么玩；主推是否明确；普通准备是否占据过多篇幅；关键期限、入口和失败应对是否仍然醒目；是否把研究核验误写成预订完成。优先使用已有每日主题和摘要，不编造体验、推荐理由或用户偏好。完整研究 JSON 保留，精简仅发生在展示层。页面继续支持手机、桌面、键盘、减少动态效果、分享与两种 PDF。标题区提供轻量“保存 PDF”和“更多”工具，复制链接、分享二维码和打印入口收进“更多”，不再设置常驻绿色分享主按钮。保存 PDF 先选择推荐的随身简版或完整资料版，再打开浏览器打印窗口；不宣称直接下载。随身简版从原数据派生全部日期与时间安排、主推餐厅、准确地址、必要费用、预约期限、入出口、最晚离开和失败应对，地图二维码只编码已有或已核验 POI 的 HTTPS 地点链接；离线仍可读地址，地图需要联网。完整版包含全部备选、路线、核验依据和来源。直接系统打印及无脚本打印默认随身简版；有脚本打印结束后恢复原日期、展开状态与视图。图片必须有合法来源与替代文本；交通卡保留准确目的地、复制和实际来源的 HTTPS 地点入口，不嵌入地图或登录页。

渲染时可用已审核的本地图片清单 `--visuals .travel-research/<trip-id>/visuals/manifest.json` 补充封面、游玩和美食图片；AI 图必须在页面标明“AI 生成”，景点图标明“非景点实景”，餐饮图标明“非实拍菜品”，不可用于证明地点、菜品或开放状态。图片嵌入单文件，素材缺失时保留清晰的文字和抽象装饰。渲染后分别检查手机和桌面宽度，修复溢出、图片失效、信息过密、时间轴错位和交互降级。用 `prepare_share.py` 将单文件 HTML 复制到项目中可见的 `travel-plans/<trip-id>/index.html`，并在最终回复给出该文件的绝对路径链接，不能只指向隐藏的 `.travel-research/`。同附 `itinerary.json`、关键假设、预约及出发前复核项。

正式 HTML 结果统一放在项目根目录下的 `travel-plans/`，每次行程使用独立子目录，不在项目根目录散放行程 HTML。`<trip-id>` 与研究工作区保持一致，新建时采用小写英文或拼音目的地（多目的地用短横线连接）加出发日期 `YYYY-MM-DD`，如 `wudangshan-2026-10-06`；相同日期的独立方案可追加有意义的短后缀。HTML 入口固定命名为 `index.html`，中文路线名称放在页面标题中；同一行程重生成复用同一路径，不新增 `最终版`、`v2` 等平行文件。`.travel-research/` 保留研究与渲染产物，`designs/` 仅用于设计探索和预览。

```bash
python3 skills/travel-planning/scripts/prepare_share.py ".travel-research/<trip-id>/artifacts/itinerary.html" --output-dir "travel-plans/<trip-id>"
```

本地 HTML 文件路径不能直接在另一台手机上打开。用户可将 `index.html` 通过隔空投送或网盘传到手机，再用浏览器打开；浏览器限制脚本时仍应能阅读并切换主要视图。手机上可使用页面“保存 PDF”，选择版本后由浏览器生成 PDF；无脚本时可使用浏览器打印保存随身简版。需要可转发的 HTTPS 链接时，先检查私人住址、姓名等敏感信息与过期动态价格，再按发布规范准备完整站点快照；生成本地文件不等于已经发布，不能把单行程目录直接覆盖到已有多行程站点。
同一行程更新已有 `index.html` 时，确认目标就是本次行程的分享文件后，使用 `prepare_share.py --replace` 覆盖；不得覆盖其他行程文件。

需要手机自由访问与转发时，可按[手机分享与发布](references/publishing.md)在本地先冻结单行程，再用 `publish_itinerary.py prepare-site` 合入最后验证的整站快照，向用户展示本次页面、保留的行程清单和目标站点；这些本地准备不构成发布授权。默认一个固定 Netlify 站点承载多份行程，链接为 `/trips/<trip-id>/`；公开的 `/history/` 列出已发布行程，不列出草稿，详情页不反向链接列表；整站状态在 `.travel-research/publication/site.json`，快照在 `travel-plans/_site/releases/`。新增行程保留旧页面，同一行程更新保留 URL，根网址继续显示第一份行程。页面“更多”中提供复制行程链接与本地生成的分享二维码；本地文件、localhost 和部署预览不提供正式分享链接。

用户审核本次 HTML 并明确确认发布后，核对待发布快照与审核版本一致，再由 Agent 调用发布器 → 匿名核对所有页面 → 同时返回 `/history/` 的完整历史列表地址、本次 `/trips/<trip-id>/` 的完整分享地址和本地备份。不能只给本次行程地址，否则用户找不到其他规划；分享给同行人时只发对应的单行程地址。凭证由发布器读取项目根目录 `.env`，不让用户逐次 export 或执行 Python。未取得本次确认，或用户要求草稿、仅本地、暂不发布时，不调用 `publish`，不为审核创建 Netlify 部署预览；本地修改不更新线上页面。待确认的旧部署先 status，写请求结果未知不盲目重试；凭证缺失或验证失败时报告准确状态，不声称已上线。

上述两个网址必须取自本次发布器核验的 Netlify 项目返回值，每个安装者的域名不同，不得硬编码本仓库示例站点的地址。用户单独问“我的历史记录在哪里”时，读取站点状态中的已验证 `history_url`；状态缺失或不确定时运行只读 `publish_itinerary.py status` 复核，再给出完整可点击地址。若还没有成功发布过任何行程，说明历史页尚未上线，不猜测 URL。

行程文字保留会改变旅行者时间、地点、动作、费用或备选的信息；水彩画面与路线叙事帮助理解和收藏，优先回答几点到、从哪里进、按什么顺序走、最晚何时离开、何时预约、花多少钱、下一段怎么走以及失败时如何调整。
